# 기술적 의사결정

## 2026-07-30: 플레이필드와 접면 판정 분리

### 배경

핵심 조작 구현 단계에서 달팽이가 바닥, 벽, 경사 구조물에 붙거나 굴러가는 동작을 빠르게 검증해야 했다. 동시에 현재 구조물이 최종 레벨 구조로 굳어지지 않도록 레벨 데이터와 접면 판정을 분리할 필요가 있었다.

### 결정

현재 필드는 `Playfield`와 `LevelDefinition`으로 구성한다. 접면 판정은 `AttachmentSurface`와 `AttachmentProbe`로 분리해 일반 상태의 접면 부착과 껍질 상태의 지지면 판정을 구분한다.

### 이유

초기 단계에서는 Tiled 기반 레벨 로더보다 코드 기반 구조물이 조작감 검증에 빠르다. 다만 접면 판정을 별도 타입으로 분리하면 이후 실제 레벨 데이터로 옮길 때 플레이어 조작 로직을 덜 흔들 수 있다.

### 영향

후속 레벨 작업에서는 필드 요소를 바닥, 벽, 발판, 경사면, 기믹, 시작점, 목표 지점, 체크포인트로 분리하고 `Playfield` 역할을 실제 레벨 로더와 접면 해석 시스템으로 확장한다.

## 2026-08-01: 기믹 케이스 씬을 메인 수직 레벨과 분리

### 배경

세로 맵은 위쪽으로 계속 확장되어야 한다. 특정 기믹을 테스트할 때마다 플레이어가 메인 맵 하단부터 해당 위치까지 이동하면 검증 속도가 떨어진다.

### 결정

메인 수직 레벨과 별도로 `PlayableCaseScene`을 둔다. 기믹 패턴은 먼저 `LevelDefinitions.ts`의 케이스 레벨로 정의하고, URL 쿼리 `case`를 통해 바로 실행한다.

케이스 목록과 검증 상태는 `notes/gimmick-cases.md`에서 관리한다.

### 이유

기믹을 작은 플레이어블 케이스에서 먼저 검증하면 이동 시간 없이 조작감과 물리 반응을 반복 확인할 수 있다. 검증된 케이스 구간은 이후 메인 수직 레벨 상단에 붙이는 방식으로 확장한다.

### 영향

`BootScene`은 `case` 쿼리 유무에 따라 `GameScene` 또는 `PlayableCaseScene`으로 분기한다. 후속 작업에서 스프링, 범퍼, 위험 지형 같은 기믹도 동일한 케이스 레벨 흐름으로 먼저 검증한다.

## 2026-08-01: 레벨을 오브젝트 목록으로 구성

### 배경

기믹 케이스가 늘어나면 케이스 Scene 자체보다 Scene을 구성하는 개별 오브젝트를 추적해야 한다. 오브젝트 하나가 단일 기믹이므로 필드, 발판, 경사면 같은 기초 요소도 같은 방식으로 관리할 필요가 있었다.

### 결정

`LevelDefinition`은 `objects` 목록을 가진다. 현재 기본 오브젝트 종류는 `field`, `surface`, `terrain`, `surface-line`이다. `Playfield`는 레벨의 오브젝트 목록에서 필드와 표면 오브젝트를 읽어 렌더링과 접면 판정을 구성한다.

### 이유

Scene을 기믹 필드로 두고, 기믹 필드를 오브젝트 조합으로 표현하면 특정 케이스에서 검증한 오브젝트 구성을 메인 수직 맵에 옮기기 쉽다. 이후 스프링, 범퍼, 바람 같은 기믹도 같은 단위로 추적할 수 있다.

### 영향

기믹 케이스 문서는 케이스뿐 아니라 기초 오브젝트 목록도 함께 추적한다. 후속 작업에서는 개별 기믹 오브젝트가 고유 `id`, 종류, 위치와 물리 설정을 가지도록 확장한다.

## 2026-07-30: Phaser 3와 Matter Physics 통합 사용

### 배경

2D 물리 기반 클라이밍 게임을 정적 웹 환경에서 실행해야 한다.

### 결정

Phaser 3를 게임 프레임워크로 사용하고, 물리 엔진은 Phaser가 제공하는 Matter Physics 통합 기능을 사용한다.

### 이유

Phaser 3는 브라우저 기반 2D 게임 제작에 적합하고, Matter Physics 통합을 통해 별도 Matter.js 의존성 없이 물리 바디와 충돌을 다룰 수 있다.

### 영향

게임 실행과 UI는 Phaser Scene 중심으로 구성한다. Matter.js를 별도 패키지로 설치하지 않는다.

## 2026-08-04: 메인 수직 맵을 Tiled 오브젝트 레이어로 관리

### 배경

도트 디자인을 반영하려면 코드 상수로 좌표를 직접 수정하는 방식보다 맵 에디터에서 지형과 기준점을 관리하는 방식이 필요하다. 다만 달팽이 접면 물리 규칙은 이미 `SurfaceEdge` 중심으로 분리되어 있으므로, 물리 규칙 전체를 바꾸기보다 맵 데이터의 출처만 바꾸는 편이 안전하다.

### 결정

메인 수직 맵은 `public/assets/tilemaps/initial-vertical.tmj` Tiled JSON 파일로 관리한다. `GameScene`은 이 파일을 로드하고, `TiledLevelLoader`가 Tiled 오브젝트 레이어를 기존 내부 `LevelDefinition`으로 변환한다.

현재 Tiled 레이어는 다음 역할을 가진다.

- `metadata`: 필드 크기와 레벨 메타 정보
- `markers`: 시작점과 도착점 같은 기준점
- `walls`: 좌우 벽 디자인 타일
- `ground`: 바닥 디자인 타일
- `terrain`: 8px 단위로 이어 붙이는 기본 땅 디자인 타일
- `surfaces`: 달팽이가 실제로 충돌하고 붙어 이동할 채워진 지형 구현체

기믹 케이스는 빠른 검증이 중요하므로 코드 기반 레벨 정의를 유지한다.

### 이유

Tiled 파일을 내부 레벨 모델로 변환하면 달팽이의 접면 선택, 미끄럼 material, 내부 진입 방어 같은 기존 규칙을 유지할 수 있다. 동시에 초기 맵 배치와 이후 도트 타일셋 반영은 Tiled에서 관리할 수 있다. 타일 지형의 픽셀 계단을 접면으로 자동 추론하면 이동 경로가 흔들리므로, 달팽이가 충돌하고 타야 하는 경로는 `surfaces` polygon/rectangle으로 명시하고 타일 레이어는 디자인 용도로 둔다.

### 영향

메인 맵 배치는 `LevelDefinitions.ts`가 아니라 Tiled 파일에서 수정한다. 후속 작업에서는 Tiled 타일 레이어를 비주얼로 사용하고, 오브젝트 레이어는 물리/접면/기믹 기준 데이터로 분리한다.
