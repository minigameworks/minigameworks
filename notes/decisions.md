# 기술적 의사결정

## 2026-07-30: 임시 플레이필드와 접면 판정 분리

### 배경

핵심 조작 구현 단계에서 달팽이가 바닥, 벽, 경사 구조물에 붙거나 굴러가는 동작을 빠르게 검증해야 했다. 동시에 현재 구조물이 최종 레벨 구조로 굳어지지 않도록 문서와 코드에서 임시 구현임을 분명히 할 필요가 있었다.

### 결정

현재 필드는 `TemporaryPlayfield`와 `TEMPORARY_PLATFORMS`로 구성한 임시 플레이필드로 유지한다. 접면 판정은 `AttachmentSurface`와 `AttachmentProbe`로 분리해 일반 상태의 접면 부착과 껍질 상태의 지지면 판정을 구분한다.

### 이유

프로토타입 단계에서는 Tiled 기반 레벨 로더보다 코드 기반 임시 구조물이 조작감 검증에 빠르다. 다만 접면 판정을 별도 타입으로 분리하면 이후 실제 레벨 데이터로 옮길 때 플레이어 조작 로직을 덜 흔들 수 있다.

### 영향

후속 레벨 작업에서는 임시 필드 요소를 그대로 확장하지 않는다. 바닥, 벽, 발판, 경사면, 기믹, 시작점, 목표 지점, 체크포인트를 별도 레벨 요소로 분리하고 `TemporaryPlayfield` 역할을 실제 레벨 로더와 접면 해석 시스템으로 대체한다.

## 2026-07-30: Phaser 3와 Matter Physics 통합 사용

### 배경

2D 물리 기반 클라이밍 게임을 정적 웹 환경에서 실행해야 한다.

### 결정

Phaser 3를 게임 프레임워크로 사용하고, 물리 엔진은 Phaser가 제공하는 Matter Physics 통합 기능을 사용한다.

### 이유

Phaser 3는 브라우저 기반 2D 게임 제작에 적합하고, Matter Physics 통합을 통해 별도 Matter.js 의존성 없이 물리 바디와 충돌을 다룰 수 있다.

### 영향

게임 실행과 UI는 Phaser Scene 중심으로 구성한다. Matter.js를 별도 패키지로 설치하지 않는다.

## 2026-07-30: 개발 문서는 notes 디렉터리에 작성

### 배경

프로젝트 문서 위치를 일관되게 유지해야 한다.

### 결정

내부 개발 문서는 `docs/`가 아니라 `notes/` 아래에 작성한다.

### 이유

작업 명세에서 지정한 문서 구조와 에이전트 작업 절차를 일관되게 따르기 위해서다.

### 영향

게임 콘셉트, 아키텍처, 개발 방법, 의사결정 문서는 모두 `notes/`에서 관리한다.
